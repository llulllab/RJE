01 · Overview

A single endpoint. A complete deliberation.

RJE exposes one operation: submit a case, receive a structured decision. The response contains a framing report, a synthesised decision, the five independent expert analyses, a vote distribution, and a fully formatted DOCX suitable for archival.

There is no SDK to install, no message queue to provision, no callback URL to register. A single HTTPS request returns the full audit-grade output in seconds.

02 · Authentication

Session tokens.

API access is provisioned per organisation against a tier (Starter, Growth, Enterprise). Request access by writing to growth.business@llulllab.com with the tier you intend, the contracting entity, and the expected use case. A session token is issued by return.

The session token is passed in the X-Session-Token header on every request. Tokens are scoped to a single organisation and may be rotated on request. Token lifecycle, including expiry and rotation policy, is set at access provisioning.

Custody

Treat the session token as a production secret. Storage in a managed secret vault is recommended. Rotation on personnel change is recommended. Compromise should be reported to growth.business@llulllab.com for immediate revocation.

03 · The request

Submit a case for deliberation.

The endpoint is POST https://api.llulllab.com/rje/v1/deliberate. Content type is application/json. The minimum viable request carries a description, a domain, and the session token.

# Submit a case for deliberation
curl -X POST https://api.llulllab.com/rje/v1/deliberate \
  -H "X-Session-Token: $RJE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "description":  "Should the new staff scheduling algorithm be approved given Article 22 of the GDPR concerning automated decisions affecting workers?",
    "domain":       "data_privacy",
    "urgency":      "normal",
    "constraints":  ["GDPR Article 22 compliance required"],
    "stakeholders": ["employees", "DPO", "operations"]
  }'

Request fields

FieldTypeDescription
descriptionstring · requiredCase description, 40 to 4,000 characters. State the decision to be made, not just the topic.
domainenum · requireddata_privacy, safety, fairness, transparency, governance, or other. Shapes which slice of the precedent library is consulted.
urgencyenum · optionallow, normal, high, critical. Recorded in the audit trail; does not change deliberation quality.
contextobject · optionalFree-form supplementary material (notes, prior approvals, internal references). Up to 16 KB.
constraintsstring[] · optionalHard requirements that any acceptable decision must satisfy.
stakeholdersstring[] · optionalParties whose interests the decision affects. Each is considered explicitly.
Tip

Write the description as the decision to be made, not the topic. "Should we approve a new staff scheduling algorithm under GDPR Article 22?" deliberates better than "GDPR Article 22 review."

04 · The response

A structured, defensible decision.

A successful response carries the full deliberation as a single JSON object. The most useful fields, in order of how compliance teams typically consume them: the final decision, the rationale, the vote distribution, the five expert analyses, and the DOCX archive.

{
  "status":              "completed",
  "case_id":             "4a885535-90b1-...",
  "preliminary_report":  "Framing of approve / reject / modify for this case ...",
  "decision": {
    "final_decision":     "modified",
    "confidence_score":   0.94,
    "decision_rationale": "..."
  },
  "voting": {
    "majority_decision":  "modified",
    "vote_counts":        { "approve": 0, "reject": 0, "modify": 5 }
  },
  "expert_analyses": [
    { "expert_id": "EXPERT_01", "position": "modify", "reasoning": "..." },
    // ... five evaluators total
  ],
  "decision_document":    "Reasoned synthesis prepared for the audit trail ...",
  "docx_base64":          "UEsDB..."
}

preliminary_reportstringCase framing produced before deliberation. Defines what approve, reject, and modify concretely mean.

05 · Status codes

Six outcomes worth handling.

200 · completed 200 · halted 400 · validation 401 · unauthenticated 429 · quota_exceeded 503 · transient_failure

Halted

The internal safety mechanism flagged the case for extreme risk patterns and refused to issue a decision. The response carries status: "halted" with an explanatory note but no decision body. Halts are deliberate, are not counted against quota, and should be routed to a human reviewer rather than retried.

Validation (400)

The request was rejected before deliberation. Common causes: description shorter than 40 characters, invalid domain enum, malformed JSON, payload exceeding 16 KB. Not billed.

Unauthenticated (401)

The session token is missing, malformed, or revoked. Verify the X-Session-Token header. Not billed.

Quota exceeded (429)

The tier's monthly included allowance, or a short-window rate limit, was exhausted. Overage pricing applies on tiers that permit it. Not billed when rejected.

Transient failure (503)

An upstream component briefly degraded. Safe to retry once after a short backoff. Auto-retry is performed internally; what reaches the client is a definitive verdict. Not billed.

06 · Retry semantics

Idempotency and quota.

Deliberation is computationally expensive; the platform protects you from accidentally double-billing.

  • Idempotency — submitting the same case twice produces two distinct case_id values and two distinct decisions. RJE is not deterministic; the precedent base shifts, the synthesis differs. If you require stable archival, store the first case_id and do not resubmit.
  • Internal retries — transient infrastructure failures are retried internally and not surfaced as 503 unless the retry also failed. You generally do not need to implement retry logic.
  • Quota accounting — only completed responses consume quota. Halts, validation rejections, unauthenticated rejections, transient failures, and rate-limit rejections do not.
07 · Operational notes

What you can rely on.

Transport

HTTPS only, encrypted in transit. Connection keep-alive is honoured.

Latency

Typical end-to-end latency for a completed deliberation is 30 to 90 seconds. The deliberation is not designed for synchronous user-facing flows; design your integration around asynchronous handoff to a reviewer queue, an email inbox, or an archival store.

Audit trail

Every deliberation is persisted with full lineage: input payload, framing report, expert analyses, vote distribution, decision document, DOCX. Case retention and retrieval terms are set per tier at access provisioning.

Data residency

Production infrastructure is hosted in the European Union. Deployment options for the Enterprise tier are discussed at contracting.
